# 项目使用手册

本文档用于帮助新成员拉取项目后快速启动、理解目录、完成业务开发和排查常见问题。它不是历史改造记录，而是一份面向日常开发的操作手册。

## 1. 项目定位

本项目基于若依前后端分离版本改造，后端使用 Spring Boot 3、Spring Security、JWT、Redis、MyBatis、MyBatis-Plus、PageHelper、MapStruct、Knife4j、EasyExcel、x-file-storage 等能力。

当前项目目标不是完全推翻若依原有体系，而是在保留若依原始功能可用的基础上，提供一套以后做业务项目可以直接复用的脚手架能力：

- 原若依系统管理、权限、菜单、字典、定时任务、代码生成等功能继续可用。
- 新业务接口推荐使用统一返回类 `Response<T>`。
- 原若依分页结构 `TableDataInfo` 保留，列表分页接口继续兼容前端表格生态。
- 文件上传改造成基于文件 ID 的业务文件生命周期管理。
- 代码生成器支持 SaveDTO、EditDTO、QueryDTO、VO、MapStruct 转换、参数校验、文件字段回显。
- 日志能力增强，支持 traceId、操作日志增强、异常日志落库和后台查看。

更细的专题说明见 [../redoc](../redoc)。

## 2. 技术栈与环境要求

### 2.1 后端

- JDK：17
- Maven：3.8 或更高版本
- Spring Boot：3.5.16
- MySQL：建议 8.x，至少使用兼容当前 SQL 的 5.7+
- Redis：6.x 或 7.x
- MyBatis-Plus：3.5.10
- MapStruct：1.6.3

### 2.2 前端

前端项目独立放在 `RuoYi-Vue3` 仓库或目录中，技术栈为 Vue 3、Vite、Element Plus、Pinia。

建议使用：

- Node.js：18 或 20
- npm、pnpm 或 yarn：按前端项目锁文件选择

### 2.3 存储

本项目已集成 x-file-storage，支持本地存储、MinIO、阿里云 OSS、腾讯云 COS 等平台。开发环境建议先用本地存储或 MinIO，生产环境再切换对象存储。

## 3. 目录结构

后端主要目录如下：

```text
RuoYi-Vue-X
+-- ruoyi-admin        # 后端启动模块，包含启动类、通用接口、后台 Controller
+-- ruoyi-common       # 通用工具、基础实体、统一返回、异常、分页、Excel 等
+-- ruoyi-framework    # 框架配置、安全、切面、异常处理、过滤器、MyBatis-Plus 自动填充
+-- ruoyi-generator    # 代码生成器、生成模板、生成配置
+-- ruoyi-quartz       # 定时任务模块
+-- ruoyi-system       # 系统业务模块，也放置部分示例业务、文件管理、异常日志服务
+-- sql                # 初始化 SQL 和增量升级 SQL
+-- doc                # 历史改造文档，保留溯源
+-- redoc              # 按功能点重新整合后的专题文档
+-- manual             # 新人使用手册
```

模块依赖关系大致如下：

```text
ruoyi-admin
  +-- ruoyi-framework
  +-- ruoyi-system
  +-- ruoyi-quartz
  +-- ruoyi-generator
  +-- ruoyi-common
```

日常开发一般会改这几类文件：

- Controller：`ruoyi-admin/src/main/java/com/ruoyi/web/controller` 或 `ruoyi-system/src/main/java/com/ruoyi/system/controller`
- Service、Mapper、Domain、DTO、VO、Convert：通常在 `ruoyi-system/src/main/java/com/ruoyi/system`
- Mapper XML：`ruoyi-system/src/main/resources/mapper`
- 代码生成模板：`ruoyi-generator/src/main/resources/vm`
- 配置文件：`ruoyi-admin/src/main/resources/application*.yml`
- 数据库脚本：`sql`

## 4. 快速启动

### 4.1 初始化数据库

创建数据库：

```sql
CREATE DATABASE `ry-vue` DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;
```

新库建议按顺序执行：

```text
sql/ry_20260417.sql
sql/quartz.sql
sql/sys_storage_file_20260901.sql
sql/sys_storage_file_access_object_key_20260908.sql
sql/sys_storage_file_url_hash_20260908.sql
sql/sys_user_avatar_20260908.sql
sql/sys_log_enhance_20261009.sql
```

如果是已有库升级，只执行尚未执行过的增量脚本。执行前建议先备份数据库。

### 4.2 修改后端配置

数据库配置在：

```text
ruoyi-admin/src/main/resources/application-druid.yml
```

把 `spring.datasource.druid.master.url`、`username`、`password` 改成自己的 MySQL 信息。项目里当前配置可能指向内网地址，第一次启动前必须检查。

Redis 配置在：

```text
ruoyi-admin/src/main/resources/application.yml
```

重点检查：

```yaml
spring:
  data:
    redis:
      host: localhost
      port: 6379
      database: 0
      password:
```

文件上传根目录也在 `application.yml`：

```yaml
ruoyi:
  profile: D:/ruoyi/uploadPath
```

Windows 开发环境可以保持类似 `D:/ruoyi/uploadPath`；Linux 或 Docker 环境建议改成 `/home/ruoyi/uploadPath` 或挂载目录。

### 4.3 开发环境存储建议

为了快速启动，开发环境建议先使用本地存储平台。检查 `application.yml` 或当前激活 profile 中的配置：

```yaml
dromara:
  x-file-storage:
    default-platform: local-1
```

如果默认平台是腾讯云 COS、阿里云 OSS 或 MinIO，需要同时配置对应平台的 endpoint、bucket、accessKey、secretKey 等信息。开源项目不建议把真实密钥提交到仓库，生产环境应通过环境变量或外部配置注入。

### 4.4 启动后端

在后端根目录执行：

```bash
mvn -pl ruoyi-admin -am -DskipTests compile
```

本地运行可以直接启动：

```text
ruoyi-admin/src/main/java/com/ruoyi/RuoYiApplication.java
```

默认服务地址：

```text
http://localhost:8080
```

接口文档地址：

```text
http://localhost:8080/doc.html
http://localhost:8080/swagger-ui.html
```

如果生产 profile 关闭了接口文档，需要在开发环境配置中打开 Knife4j / Springdoc。

### 4.5 启动前端

前端在独立目录，例如：

```text
D:/workspace/p_project/RuoYi/RuoYi-Vue3
```

进入前端目录后执行：

```bash
npm install
npm run dev
```

确认前端开发代理指向后端 `http://localhost:8080`。若依 Vue3 项目通常通过 `.env.development` 和 `vite.config.js` 配置 `/dev-api` 代理。

默认登录账号如果初始化 SQL 未修改，一般为：

```text
admin / admin123
```

## 5. 配置说明

### 5.1 Profile

当前 `application.yml` 中使用：

```yaml
spring:
  profiles:
    active: druid,prod
```

这表示会同时加载 `application-druid.yml` 和 `application-prod.yml`。如果本地开发不希望加载生产对象存储配置，可以新增 `application-dev.yml`，并把激活环境改为：

```yaml
spring:
  profiles:
    active: druid,dev
```

建议约定：

- `dev`：本地开发，连接本地 MySQL、Redis、本地文件存储或 MinIO。
- `test`：测试环境，连接测试库和测试存储。
- `prod`：生产环境，只通过环境变量或配置中心注入敏感信息。

### 5.2 上传场景

上传场景配置在 `ruoyi.upload-scenes`：

```yaml
ruoyi:
  upload-scenes:
    avatar:
      access: public
      path-prefix: avatar
      max-size: 5MB
      allowed-extension: png,jpg,jpeg
    commonImg:
      access: public
      path-prefix: image
      max-size: 5MB
      allowed-extension: png,jpg,jpeg
    commonFile:
      access: private
      path-prefix: file
      max-size: 5MB
      allowed-extension: doc,xls,ppt,txt,pdf
```

前端上传时传 `uploadScene`，后端按场景限制文件大小、扩展名、访问级别和路径前缀。新业务不要在 Controller 里硬编码文件规则，优先新增或复用上传场景。

### 5.3 文件访问策略

文件管理配置在 `ruoyi.storage-file`：

- `access-url-mode`：公开文件访问地址模式，支持直连、域名、后端代理等模式。
- `public-domain`：公开文件域名。
- `require-upload-scene`：是否要求通用上传必须传 `uploadScene`。
- `temp-expire-hours`：临时文件未绑定业务时允许清理的时间。
- `access-token-expire-seconds`：私有文件临时访问 token 有效期。
- `default-delete-delay-hours`：业务解绑后待删除文件默认保留时间。

详细设计见 [../redoc/01-文件存储与上传体系.md](../redoc/01-文件存储与上传体系.md)。

## 6. 新业务开发规范

### 6.1 推荐分层

新业务推荐使用下面的结构：

```text
domain      # 数据库实体
dto         # SaveDTO、EditDTO、QueryDTO
vo          # 返回给前端的展示对象
convert     # MapStruct 转换器
mapper      # Mapper 接口
service     # Service 接口
serviceImpl # Service 实现
controller  # Controller
```

命名示例：

```text
Node.java
NodeSaveDto.java
NodeEditDto.java
NodeQueryDto.java
NodeVo.java
NodeConvert.java
NodeMapper.java
INodeService.java
NodeServiceImpl.java
NodeController.java
```

### 6.2 Controller 返回规范

新业务建议：

- 分页列表：继续返回 `TableDataInfo`
- 详情查询：返回 `Response<VO>`
- 新增、修改、删除：返回 `Response<Void>`
- 需要返回业务结果时：返回 `Response<T>`

分页继续保留若依原始结构，是为了兼容现有表格、分页、导出等生态：

```java
@GetMapping("/list")
public TableDataInfo list(QueryDto query) {
    startPage();
    List<Vo> list = service.selectList(query);
    return getDataTable(list);
}
```

新增、修改、删除可以使用：

```java
@PostMapping
public Response<Void> add(@Validated @RequestBody SaveDto dto) {
    return Response.toResponse(service.insert(dto));
}
```

`service.insert(dto)` 默认返回 `int`，表示影响行数。`Response.toResponse(int rows)` 用于把影响行数转换为统一返回。

### 6.3 AjaxResult、R 与 Response 的关系

项目保留若依原有 `AjaxResult`、`R` 和 `TableDataInfo`，不强制改造历史接口。建议规则是：

- 若依原有系统接口：保持原样，避免破坏已有前端和权限管理。
- 新业务接口：使用 `Response<T>`。
- 分页接口：继续使用 `TableDataInfo`。
- 文件下载、Excel 导出、验证码等特殊响应：按原若依方式处理。

这样能兼顾向后兼容和新业务规范。

### 6.4 参数校验

SaveDTO 和 EditDTO 推荐加 Bean Validation 注解：

```java
@NotBlank(message = "名称不能为空")
private String name;
```

Controller 入参使用：

```java
@Validated @RequestBody SaveDto dto
```

校验失败会进入全局异常处理，返回统一错误信息。新增时一般校验必填字段；编辑时根据业务需要决定是否必填。

### 6.5 PUT 与 PATCH

当前生成和业务习惯更接近“全量编辑”，可以继续使用 `PUT`。如果以后要做局部更新，也就是只传部分字段并且忽略 null，需要单独设计 Patch DTO 和更新逻辑，不建议混在普通编辑接口里。

## 7. 持久层与 MapStruct

### 7.1 XML 与 MyBatis-Plus 的关系

本项目保留若依原有 XML Mapper 写法，同时集成 MyBatis-Plus：

- 代码生成模板默认仍然生成 XML，适合清晰控制 SQL。
- 简单 CRUD 或业务自定义模块可以使用 MyBatis-Plus API。
- 使用 MP API 时，自动填充由 `MetaObjectHandler` 处理。

### 7.2 新增、修改、删除返回什么

Service 层新增、修改、删除推荐返回 `int`：

```java
int insertXxx(XxxSaveDto dto);

int updateXxx(XxxEditDto dto);

int deleteXxxByIds(Long[] ids);
```

如果内部使用 MyBatis-Plus 的 `save`、`updateById`、`removeByIds`，它们通常返回 `boolean`，Service 层可以转换成 `int`：

```java
return save(entity) ? 1 : 0;
```

Controller 层继续通过 `Response.toResponse(rows)` 返回。

### 7.3 MapStruct 使用建议

MapStruct 用于 DTO、Entity、VO 之间转换。典型写法：

```java
@Mapper(componentModel = "spring")
public interface XxxConvert {
    Xxx toEntity(XxxSaveDto dto);

    Xxx toEntity(XxxEditDto dto);

    XxxVo toVo(Xxx entity);

    List<XxxVo> toVoList(List<Xxx> list);
}
```

`componentModel = "spring"` 表示转换器由 Spring 管理，可以通过依赖注入使用：

```java
@Resource
private XxxConvert xxxConvert;
```

如果某些字段不需要转换，可以在具体方法上显式忽略。不要为了省事在业务里大量手写 Bean copy，否则后续字段调整容易漏。

详细规范见 [../redoc/05-持久层与对象转换规范.md](../redoc/05-持久层与对象转换规范.md)。

### 7.4 自动填充

项目引入了 MyBatis-Plus 自动填充，用于在使用 MP API 时自动处理创建人、更新人、创建时间、更新时间等字段。

需要注意：

- 若依原始 XML 写法中，很多字段仍然由业务代码或 SQL 显式赋值。
- 使用 MP 的 `insert`、`updateById` 等 API 时，自动填充才会更明显地发挥作用。
- 新业务如果继续使用 XML，按模板生成的 SQL 走即可。

## 8. 文件上传与业务文件生命周期

### 8.1 核心原则

新业务文件字段推荐存文件 ID，而不是直接存 URL。

原因：

- URL 可能随存储平台、访问策略、域名、代理方式变化。
- 文件 ID 稳定，可以关联文件记录、访问权限、临时文件、待删除状态。
- 私有文件需要后端鉴权后返回临时访问地址，不能直接暴露真实地址。

### 8.2 前端组件 value-type

前端文件上传组件支持：

```vue
<image-upload v-model="form.imageId" value-type="fileId" upload-scene="commonImg" />
<file-upload v-model="form.fileId" value-type="fileId" upload-scene="commonFile" />
```

`value-type="fileId"` 表示组件提交给后端的是文件 ID。这里不加冒号，因为它是普通字符串。

如果要传变量才加冒号：

```vue
<file-upload :limit="3" :file-size="10" :file-type="['pdf', 'doc']" />
```

`:` 表示绑定 JavaScript 表达式，不加 `:` 表示字符串字面量。

### 8.3 VO 回显

业务表只保存文件 ID。查询列表或详情时，后端 VO 需要补充文件展示信息：

```java
private String file1;

private List<StorageFileVo> file1FileList;
```

图片回显由前端组件根据文件列表中的预览地址展示；附件回显使用原文件名展示。业务页面不应该每个地方都手写 `previewUrl || fileId`、`originalFilename` 这类逻辑，优先放到通用组件或生成模板里。

### 8.4 新增、修改、删除时的文件同步

文件生命周期大致是：

```text
上传文件
  -> 写入 sys_storage_file，状态为临时或未绑定
  -> 新增业务数据后绑定 bizType、bizId、bizField
  -> 修改业务数据时同步新增绑定、旧文件标记待删除
  -> 删除业务数据时文件标记待删除
  -> 定时任务清理过期临时文件和待删除文件
```

新业务如果有文件字段，优先使用生成器生成对应的 DTO、VO、文件绑定逻辑和前端上传组件。

详细说明见：

- [../redoc/01-文件存储与上传体系.md](../redoc/01-文件存储与上传体系.md)
- [../redoc/02-业务文件生命周期与前端回显.md](../redoc/02-业务文件生命周期与前端回显.md)

## 9. 代码生成器使用

### 9.1 基本流程

1. 在数据库中建好业务表。
2. 进入系统菜单“代码生成”。
3. 导入业务表。
4. 编辑表配置、字段配置、生成包名、模块名、业务名、菜单名。
5. 配置字段的列表、查询、插入、编辑、必填、显示类型。
6. 对图片或附件字段，选择对应的上传组件。
7. 生成代码并放入后端、前端对应目录。
8. 执行生成的菜单 SQL。
9. 重启后端，刷新前端菜单和权限。

### 9.2 字段生成规则

当前生成器增强后的推荐规则：

- “列表显示”为 true 的字段进入 VO。
- “插入”为 true 的字段进入 SaveDTO。
- “编辑”为 true 的字段进入 EditDTO。
- “查询”为 true 的字段进入 QueryDTO。
- 图片上传或文件上传字段会生成对应文件列表字段，用于前端回显。
- 生成 Controller 使用 `Response` 和 `TableDataInfo` 的混合规范。
- 生成 Convert 使用 MapStruct。
- 生成 DTO 时按字段配置生成校验注解。

### 9.3 前端模板

前端模板会根据字段组件类型生成：

- 普通输入框、下拉框、日期选择等表单项。
- 图片上传组件。
- 附件上传组件。
- 表格图片预览列。
- 表格附件原文件名展示列。

如果生成后业务有特殊展示要求，可以在生成代码基础上局部调整，但不要把通用文件回显逻辑散落到每个业务页面。

详细说明见 [../redoc/03-代码生成体系.md](../redoc/03-代码生成体系.md)。

## 10. 接口返回与异常处理

### 10.1 Response 结构

新业务普通接口返回：

```json
{
  "success": true,
  "message": "操作成功",
  "errorCode": null,
  "data": {}
}
```

失败时：

```json
{
  "success": false,
  "message": "错误信息",
  "errorCode": "xxx",
  "data": null
}
```

### 10.2 BizException

业务主动抛错使用 `BizException`。例如：

```java
throw new BizException("数据状态不允许删除");
```

全局异常处理会捕获并返回 `Response<Void>` 错误结果。

### 10.3 为什么异常返回 Response<Void>

异常响应没有业务数据，`Void` 比 `Object` 更明确：它表达“这个响应不会携带 data”。前端只需要读取 `success`、`message`、`errorCode` 即可。

### 10.4 原若依接口是否受影响

项目的策略是：原若依已有业务尽量保持原样，新业务逐步使用 `Response`。全局异常返回 `Response` 后，前端请求拦截器需要兼容 `Response` 与若依原有 `AjaxResult`。这部分已在前端适配过，新增页面按新规范开发即可。

详细说明见 [../redoc/04-统一返回与异常处理.md](../redoc/04-统一返回与异常处理.md)。

## 11. 日志、traceId 与异常日志

### 11.1 traceId 有什么用

每个请求会生成或透传 traceId：

- 应用日志带 traceId。
- 响应头返回 `X-Trace-Id`。
- 操作日志记录 traceId。
- 异常日志记录 traceId。

当用户反馈“某个操作失败”时，可以用 traceId 把前端请求、操作日志、异常日志、应用日志串起来。没有 traceId 时，只能靠时间、用户、接口模糊搜索，排查效率会差很多。

### 11.2 异常日志页面

项目新增了异常日志落库和后台页面。后端异常发生时，会记录：

- traceId
- 请求地址和方法
- 用户信息
- 异常类型
- 异常消息
- 堆栈摘要
- 请求参数摘要
- 创建时间

这样在不接入 GrayLog、ELK、Loki 的情况下，也能在后台页面直接看到异常。对于开源脚手架，这是更轻量、开箱即用的方案。

### 11.3 操作日志增强

操作日志增强了：

- traceId
- userId
- bizType
- bizId
- 请求参数和响应摘要脱敏、截断
- 异常信息关联

业务关键操作建议加 `@Log`：

```java
@Log(title = "节点管理", businessType = BusinessType.INSERT, bizType = "node")
```

如果能拿到业务 ID，可以继续配置 `bizId` 表达式，方便后续按业务对象追踪。

详细说明见 [../redoc/07-日志观测与异常日志.md](../redoc/07-日志观测与异常日志.md)。

## 12. 前端联调与部署

### 12.1 开发联调

开发环境推荐：

```text
浏览器 -> Vite dev server -> /dev-api 代理 -> 后端 http://localhost:8080
```

好处是：

- 前端热更新快。
- 不需要处理浏览器跨域。
- 后端保持本地直连调试。

### 12.2 生产部署

生产环境推荐：

```text
浏览器
  -> Nginx 静态资源
  -> Nginx /prod-api 反向代理
  -> 后端 ruoyi-admin jar
  -> MySQL / Redis / 对象存储
```

前端先执行：

```bash
npm run build:prod
```

构建出的 `dist` 放到 Nginx 静态目录。Nginx 同时配置接口代理，例如：

```nginx
location / {
    root /usr/share/nginx/html;
    try_files $uri $uri/ /index.html;
}

location /prod-api/ {
    proxy_pass http://ruoyi-admin:8080/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

### 12.3 Docker Compose 建议

Docker Compose 用于一键拉起一组服务。这个项目如果做完整本地或测试环境编排，通常包含：

- MySQL
- Redis
- 后端应用 `ruoyi-admin`
- Nginx 前端静态站点
- MinIO，可选，用于本地对象存储

前端可以有两种做法：

- 先在 CI/CD 中打包，再把 `dist` 放进 Nginx 镜像。
- 在前端 Dockerfile 中执行构建，再复制 `dist` 到 Nginx 镜像。

生产更推荐交给 CI/CD 构建镜像，再由 Docker Compose 或 Kubernetes 部署。

## 13. 常见开发任务

### 13.1 新增一个普通 CRUD

1. 建表。
2. 用代码生成器导入表。
3. 配置字段显示、查询、插入、编辑、校验。
4. 生成后端代码、前端代码和菜单 SQL。
5. 后端放入对应模块，前端放入对应 views/api 目录。
6. 执行菜单 SQL。
7. 重启后端，刷新前端权限。
8. 测试列表、新增、编辑、删除、导出。

### 13.2 新增一个带图片的业务

1. 表里保存图片文件 ID 字段，例如 `cover_file_id`。
2. 代码生成器中把该字段组件设为图片上传。
3. 插入、编辑字段按业务需要勾选。
4. 列表显示需要勾选时，VO 会包含文件展示信息。
5. 前端使用图片上传组件，`value-type="fileId"`。
6. Service 新增、修改、删除时同步业务文件生命周期。

### 13.3 新增一个带附件的业务

1. 表里保存附件文件 ID 字段，例如 `contract_file_id`。
2. 组件设为文件上传。
3. 上传场景通常使用 `commonFile`。
4. VO 返回文件列表，前端表格展示原文件名。
5. 私有附件下载由后端鉴权后返回临时访问地址。

### 13.4 新增一个自定义接口

建议模板：

```java
@RestController
@RequestMapping("/system/demo")
public class DemoController extends BaseController {
    @Resource
    private IDemoService demoService;

    @GetMapping("/list")
    public TableDataInfo list(DemoQueryDto query) {
        startPage();
        return getDataTable(demoService.selectList(query));
    }

    @GetMapping("/{id}")
    public Response<DemoVo> getInfo(@PathVariable Long id) {
        return Response.success(demoService.selectById(id));
    }

    @PostMapping
    public Response<Void> add(@Validated @RequestBody DemoSaveDto dto) {
        return Response.toResponse(demoService.insertDemo(dto));
    }

    @PutMapping
    public Response<Void> edit(@Validated @RequestBody DemoEditDto dto) {
        return Response.toResponse(demoService.updateDemo(dto));
    }

    @DeleteMapping("/{ids}")
    public Response<Void> remove(@PathVariable Long[] ids) {
        return Response.toResponse(demoService.deleteDemoByIds(ids));
    }
}
```

## 14. 常见问题

### 14.1 启动时报数据库连接失败

检查：

- MySQL 是否启动。
- 数据库名是否为配置中的 `ry-vue`。
- `application-druid.yml` 中 URL、账号、密码是否正确。
- MySQL 用户是否允许当前机器连接。
- 时区参数 `serverTimezone=GMT%2B8` 是否保留。

### 14.2 启动时报 Redis 连接失败

检查：

- Redis 是否启动。
- `spring.data.redis.host` 是否仍指向历史内网地址。
- Redis 是否设置密码。
- 本地防火墙或 Docker 端口是否开放。

### 14.3 登录成功但菜单不显示

检查：

- 菜单 SQL 是否执行。
- 当前用户角色是否分配了菜单权限。
- 前端是否刷新了路由和权限缓存。
- 后端接口是否返回 401、403 或菜单数据为空。

### 14.4 文件上传失败

检查：

- `uploadScene` 是否传递。
- 上传场景是否存在。
- 文件扩展名是否在 `allowed-extension` 中。
- 文件大小是否超过 `max-size` 或 Spring multipart 限制。
- 默认存储平台是否可用。
- 本地上传目录是否有写权限。

### 14.5 图片或附件上传后不回显

检查：

- 前端组件是否设置 `value-type="fileId"`。
- 表单字段保存的是否是文件 ID。
- 查询详情接口是否返回了对应的 `xxxFileList`。
- VO 组装时是否调用了文件展示信息组装逻辑。
- 私有文件访问 token 是否过期。

### 14.6 前端刷新页面 404

这是前端 history 路由常见问题。Nginx 需要配置：

```nginx
try_files $uri $uri/ /index.html;
```

### 14.7 前端接口 404

检查：

- 开发环境代理 `/dev-api` 是否指向后端。
- 生产环境代理 `/prod-api` 是否转发到后端。
- 后端 `server.servlet.context-path` 是否为 `/`。
- 前端接口路径是否多拼或少拼了前缀。

### 14.8 文档或终端显示乱码

项目中部分历史文件可能存在编码显示问题。建议：

- 新增文档和代码统一使用 UTF-8。
- IDE 文件编码设置为 UTF-8。
- Maven 编译编码使用父 POM 中的 `project.build.sourceEncoding=UTF-8`。
- Windows 终端如果显示异常，优先确认文件实际编码，再判断是否只是终端 code page 问题。

新增文档不要从乱码终端输出中复制中文内容。
