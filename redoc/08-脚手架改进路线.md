## 原文：doc/改进.md

我仔细过了一遍，现在这套已经从“能上传”到了“可管理的雏形”，但还没到完全稳。按优先级我建议这样补：

**P0 必补**
1. **私有文件下载要做业务授权**

   现在 `/common/storage/download` 只要登录并知道 URL，就能下载私有文件。应该按 `sys_storage_file.biz_type + biz_id` 做权限判断，比如当前用户只能下载自己业务范围内的附件。否则 URL 泄露后，同系统用户可能越权下载。

2. **业务保存成功后要统一绑定文件**

   现在我只看到头像业务调用了 `bindStorageFile`。点位管理这些上传字段如果保存业务后不绑定，文件记录会一直是 `file_status=0 临时`，后续清理任务可能误删真实在用文件。需要形成通用约定：业务新增/修改成功后绑定本次提交的文件 URL 到 `bizType/bizId`。

3. **业务替换/删除时统一标记旧文件待删除**

   头像已经做了一点，其他业务文件也要接入。否则只上传不清理，COS/OSS 会慢慢堆垃圾文件。

**P1 建议补**
4. **分片上传初始化也要同步 access/ACL**

   普通上传已经按场景设置 ACL，但 `initiateMultipartUpload` 目前只按场景生成路径，没有给分片初始化对象设置 ACL。大文件如果以后用于公开视频/公开资源，会遇到类似 COS `AccessDenied` 的问题。

5. **上传接口建议可配置“必须传 uploadScene”**

   不传场景时现在会走默认白名单和默认大小，适合兼容旧逻辑，但新业务最好强制传 `uploadScene`。可以加配置，例如 `ruoyi.storage-file.require-upload-scene: true`，生产打开，开发或老接口可关闭。

6. **文件返回 DTO 化**

   `CommonController` 现在用 `Map<String,Object>` 拼返回，字段容易散。建议建 `StorageFileUploadRespDTO`、`StorageFilePartRespDTO`，以后前端、接口文档、代码生成都更清楚。

7. **图片组件支持缩略图回显**

   后端已经返回 `thUrl`，但前端 `ImageUpload` 现在保存和展示都主要用 `fileName/url`。更理想是：业务保存原图 URL，列表卡片展示缩略图 URL，预览打开原图 URL。

**P2 可以后续优化**
8. **上传异常日志增强**

   现在 catch 后直接 `AjaxResult.error(e.getMessage())`，后端没有完整日志。建议上传失败时记录 `platform、uploadScene、originalFilename、size`，排查 COS/OSS 问题会快很多。

9. **前端私有文件判断不要只靠 `/private/` 字符串**

   现在够用，但更稳是后端返回 `access` 字段，前端按 `access === 'private'` 决定走后端下载。这样以后路径规则变了也不影响前端。

10. **配置密钥不要放进 application.yml**

现在腾讯 COS `secret-id/secret-key` 是明文。生产建议改成环境变量或配置中心占位，例如 `${TENCENT_COS_SECRET_ID}`。

我建议下一步先做这三个：**业务绑定通用方法、私有下载授权、分片初始化 ACL**。这三个补完，上传模块的安全和生命周期闭环会踏实很多。

## 原文：doc/改进2.md

我建议：**现在不要全加。**

对你这个若依开箱即用脚手架来说，当前做到：

```text
短期 token
短期 token + 当前登录用户校验
```

已经够作为默认内置能力了。

剩下几种我建议这样处理：

| 能力 | 是否现在加 | 原因 |
|---|---|---|
| IP/设备绑定 | 暂时不加 | 后台系统常有代理、内网、Nginx、移动网络，IP 容易变化，误伤用户 |
| 一次性使用 | 暂时不加 | 图片预览、浏览器重试、下载失败重试都会出问题，体验很差 |
| 下载审计 | 可以下一版加 | 价值高，副作用小，适合脚手架 |
| 水印/脱敏 | 不做默认能力 | 强业务相关，不同文件类型处理方式完全不同 |

**最推荐下一步加的是下载审计。**

因为它不改变访问链路，也不影响前端体验，却能解决很多实际问题：

```text
谁下载了
什么时候下载
下载哪个 fileId
属于哪个 bizType/bizId
成功还是失败
IP/UserAgent 是什么
```

这个对私有文件非常有价值，而且符合若依已有的 `sys_oper_log` 思路。

**IP/设备绑定为什么不建议默认加**

比如用户在公司网络后面：

```text
浏览器请求业务接口 IP = 网关 A
下载文件时 IP = 网关 B
```

或者经过代理、负载均衡，IP 可能变。  
你一绑定 IP，用户自己刚拿到的链接都可能下载失败。

**一次性使用为什么不建议默认加**

浏览器很容易触发重复请求：

```text
预览加载一次
失败重试一次
下载工具探测一次
用户点了两次
```

一次性 token 很容易把正常操作干掉。

**水印/脱敏为什么不建议默认加**

这个不是文件基础设施能通吃的：

- 图片水印是一套
- PDF 水印是一套
- Word/Excel 脱敏是一套
- 视频水印又是一套
- 文本脱敏还要业务字段规则

适合做扩展接口，不适合默认实现。

所以最终建议：

**当前版保留两档：**

```text
普通私有：短期 token
高敏感私有：短期 token + 当前登录用户
```

**下一版只补：**

```text
下载审计
```

这才是收益最大、风险最小的继续完善方向。
